# Module 5 — Vessel Attribution / AIS Correlation

## Purpose

Given a probable oil-spill origin (a location + radius) and an estimated
origin time window from **Module 4**, this module:

1. Loads AIS vessel-position data (synthetic for now, real later).
2. Filters it down to vessels that were plausibly in the right place at
   the right time.
3. Scores each candidate vessel on distance, time overlap, trajectory
   consistency, and AIS reporting continuity.
4. Ranks the candidates and writes two files for **Module 6** (the
   dashboard) to visualize.

The output is explicitly a **correlation / investigation score** — a way
to prioritize which vessels deserve human investigation. It is **not** a
probability of guilt and **not** proof of responsibility.

## Architecture

```
Module 4 JSON (origin_zone + time_window)
        │
        ▼
processing.load_module4_output()
        │
        ▼
AIS source (synthetic_ais.py OR a real AIS CSV export)
        │
        ▼
processing.load_ais_csv()          <- validates & standardizes AIS
        │
        ▼
processing.spatial_filter()        <- haversine distance to origin
        │
        ▼
processing.temporal_filter()       <- origin time window ± buffer
        │
        ▼
processing.extract_candidates()    <- group by vessel, drop short tracks
        │
        ▼
scoring.compute_vessel_score()     <- per-vessel score breakdown
        │
        ▼
ranking.rank_candidates()          <- sort + top N
        │
        ▼
ranking.write_outputs()            <- vessel_candidates.json
                                       vessel_tracks.geojson
```

`synthetic_ais.py` is deliberately isolated from everything else. It is
the *only* file that knows the AIS data is fake — every other file just
consumes a standard-schema CSV.

**Why these new files were added on top of the existing `processing.py`
and `scoring.py`:**

- `config.py` — every threshold (time buffer, distance decay, gap
  thresholds, score weights) lives in one dataclass instead of being a
  magic number buried in some function. Re-tuning the pipeline, or
  documenting exactly what was used for a given demo run, means editing
  one file.
- `geo_utils.py` — both spatial filtering (processing.py) and distance
  scoring (scoring.py) need haversine distance and bearing calculations.
  Putting the math in one place avoids two slightly-different
  implementations drifting apart.
- `synthetic_ais.py` — kept fully separate so nobody can accidentally
  make the "real" pipeline logic depend on synthetic-data assumptions.
  Swapping in real AIS later means deleting/ignoring this file, not
  editing processing.py or scoring.py.
- `ranking.py` — separates "how do I turn a list of per-vessel score
  objects into ranked JSON/GeoJSON files" from "how do I compute one
  vessel's score" (scoring.py). Keeps scoring.py focused purely on
  scoring math.
- `main.py` — a single, runnable entry point so the whole pipeline is
  one command, and so Module 6 / your teammates can see exactly how the
  pieces fit together.
- `tests/` — pytest suite that pins down expected behaviour (see
  Testing below) so future changes don't silently break the demo
  scenario.

## Module 4 input schema

```json
{
  "origin_zone": {
    "type": "circle",
    "center": [14.50, 74.85],
    "radius_km": 15
  },
  "time_window": {
    "start": "2026-08-20T10:00:00Z",
    "end": "2026-08-20T18:00:00Z"
  },
  "confidence": 0.82
}
```

Only `type: "circle"` is currently supported. `processing.load_module4_output()`
validates the required keys and raises a clear `ValueError` if the file
doesn't match this shape — nothing in Module 5 hard-codes the
coordinates or times found in this file; they are always read from here.

## AIS schema

| Field         | Type      | Why it's needed |
|---------------|-----------|------------------|
| `mmsi`        | string    | Unique vessel identifier — the key everything is grouped by. |
| `vessel_name` | string    | Human-readable label for the dashboard/report; not used in any calculation. |
| `timestamp`   | datetime (UTC) | Needed for temporal filtering, time-match scoring, and gap/continuity detection. |
| `latitude`, `longitude` | float | Needed for spatial filtering, distance scoring, and trajectory construction. |
| `sog`         | float (knots) | Speed over ground — used for the speed-jump anomaly check. |
| `cog`         | float (0-360°) | Course over ground — used for trajectory-heading scoring and course-jump anomaly checks. |
| `heading`     | float (0-360°) | Vessel's true heading; kept alongside `cog` for completeness (AIS reports both, they can differ e.g. under drift/current) but not currently used in scoring — a documented option for future refinement, not added just for the sake of "looking realistic". |

No other AIS fields (ship type, draught, destination, etc.) are used —
they weren't needed for any of the current scoring components, and
adding unused columns would just be noise.

## Synthetic AIS design

`synthetic_ais.py` builds trajectories around whatever origin/time window
is in the Module 4 input (never hard-coded):

- **Vessel A** (`419000001`, MV KAVERI STAR) — transits through the
  origin zone during the window, reports every 5 minutes. Should rank #1.
- **Vessel B** (`419000002`, MV COASTAL BREEZE) — passes close to the
  origin, but its track ends an hour before the window opens. Zero
  overlap with the *unbuffered* window (so its time-match score is 0),
  but its tail still falls inside the default 2-hour buffer (so it's
  still *filtered in* as a candidate and scored — not silently dropped).
- **Vessel C** (`419000003`, MV NORTHERN TRADER) — active for the whole
  window (correct timing) but stays ~35-40 km from the origin the whole
  time. Should get a low distance score.
- **Vessel D** (`419000004`, MV SILVER TIDE) — passes near the origin
  during the window, but has a ~90 minute AIS reporting gap plus an
  abrupt speed/course change right after the gap. Should get a reduced
  continuity score and trigger anomaly flags.
- **Background vessels** (`419000010-012`) — ordinary traffic far enough
  away that they're dropped at the spatial-filter stage.

Regenerate at any time with:

```bash
python -m module5_ais.synthetic_ais --module4-input data/sample/mock_module4_output.json --out data/sample/synthetic_ais.csv
```

## Spatial filtering

`processing.spatial_filter()` computes the great-circle (haversine)
distance from every AIS record to the origin center — not a raw
lat/lon-difference comparison, which would be measurably wrong here
(a degree of longitude is a different real-world distance depending on
latitude). Records within `radius_km * config.spatial_filter_factor`
(default: 3× the origin radius, so 45 km for a 15 km radius) are kept.

This cutoff is intentionally *wider* than the origin radius: a vessel
40 km away should still be considered and scored low, not silently
excluded from the candidate pool before it even gets a chance to be
ranked.

## Temporal filtering

`processing.temporal_filter()` keeps records within
`[window_start - buffer, window_end + buffer]`, where the buffer
(`config.time_buffer_hours`, default 2.0 hours) exists because Module
4's estimated time window is a *model output with uncertainty*, not a
measured fact. A hard cutoff at the exact window risks dropping the real
source vessel over an hour of drift-model timing error. The buffer is a
config value, not a hard-coded assumption — widen it if Module 4 reports
larger timing uncertainty for a given case, narrow it if the estimate is
tight.

## Trajectory construction

Candidate vessel tracks are handled as plain, sorted pandas DataFrames
(`processing.extract_candidates()`), not MovingPandas `Trajectory`
objects. **MovingPandas was deliberately not used**: our AIS schema
already includes `sog` and `cog` directly from the vessel's own
transponder, so we don't need MovingPandas' speed/direction-derivation
features. Everything the current scoring needs — closest approach,
heading, gap detection — is a few lines of pandas/haversine math.
Pulling in MovingPandas here would be extra dependency weight for no
functional gain at this stage. If the team later wants stop-detection,
trajectory simplification, or resampling, MovingPandas is a reasonable
upgrade at that point — see "Future improvements" below.

## Scoring

All four scores are in **[0, 1]**, and the overall score is the fixed
weighted combination from the SLICKTRACE master plan:

```
overall_score = 0.40 * distance_score
              + 0.30 * time_score
              + 0.20 * trajectory_score
              + 0.10 * continuity_score
```

- **Distance score** — 1.0 if the vessel's closest approach is exactly
  at the origin center, decaying linearly to 0.0 at
  `radius_km * distance_decay_factor` (default 3×radius).
- **Time-match score** — fraction of Module 4's *unbuffered* time window
  that the vessel's own timespan overlaps. 1.0 = present the whole
  window; 0.0 = no overlap at all.
- **Trajectory-match score** — a transparent heuristic: 70% heading
  consistency (does the vessel's course-over-ground at its earliest
  known position point roughly toward the origin?) + 30% whether the
  closest approach is an interior point of the track (i.e. it actually
  passed through/near the area, not just started or ended there). This
  is *not* a physics-based drift/maneuvering model — see the docstring
  in `scoring.trajectory_score()` for its explicit limitations.
- **AIS continuity score** — based purely on reporting gaps and interval
  regularity (70% largest-gap penalty, 30% interval-regularity penalty).
  A low score is a *suspicious signal*, not proof of a deliberate AIS
  shutdown — equipment faults and poor reception look the same.

## Anomaly detection (separate from the overall score)

Behavioural anomalies (sudden speed/course jumps) are a different kind
of signal from AIS continuity, and folding them into the fixed
40/30/20/10 formula would quietly change what those weights mean. So:

- `scoring.rule_based_anomaly()` (**always runs**) flags abrupt speed
  jumps (`config.anomaly_speed_jump_knots`, default 15 kn), course jumps
  (`config.anomaly_course_jump_degrees`, default 90°), and AIS gaps —
  and reports them as plain, explainable text flags.
- `scoring.isolation_forest_anomaly_scores()` (**optional**,
  `config.use_isolation_forest = False` by default) fits an
  `IsolationForest` over the candidate vessels' behaviour features
  (speed jump, course jump, gap length) and blends its normalized score
  into the reported `behavior_anomaly_score`.

**Why Isolation Forest is optional, not primary:** at this stage of the
pipeline we only have the *narrowed candidate pool* — typically a
handful of vessels — not the full background AIS traffic. An anomaly
detector needs a reasonable sample of "normal" to contrast against;
5-15 rows is too few for its output to be statistically meaningful. The
rule-based method already covers the concrete behaviours that matter
(speed jumps, course jumps, gaps) and is fully explainable to a human
investigator, which matters more than a black-box score at this stage.
If the team wants to strengthen this later, fit the Isolation Forest on
a much larger *background* AIS sample (all regional traffic over a
longer period), not just the filtered candidates.

**Anomaly info never changes `overall_score`.** It is reported alongside
the ranked candidate for a human investigator to weigh, exactly because
automatically penalizing "went dark" vessels risks either hiding the
real suspect (who may not behave anomalously at all) or wrongly
demoting an innocent vessel with a flaky AIS unit.

### `vessel_tracks.geojson`

A `FeatureCollection` of `LineString` features, one per ranked candidate,
with `[longitude, latitude]` coordinate order (GeoJSON's required order —
double-checked in the test suite to catch an accidental lat/lon swap).
Properties include `rank`, `mmsi`, `vessel_name`, `score`, `start_time`,
`end_time`, `closest_approach_km` — enough for Module 6 to color/label
tracks without a second lookup.

## Integration with Module 6

Module 6 can load both files directly:

- `vessel_candidates.json` → render the ranked candidate table / info
  panel (rank, name, score, score breakdown, closest approach, anomaly
  flags).
- `vessel_tracks.geojson` → `L.geoJSON(data).addTo(map)` in Leaflet (or
  the Mapbox GL equivalent) to draw each candidate's track, colored/sized
  by `properties.score` or `properties.rank`.

Module 5 does not build any UI itself — it only guarantees these two
files exist, in this schema, in `data/processed/`, after `main.py` runs.

```bash
pip install -r requirements.txt

```

`data/processed/vessel_candidates.json` and

## Replacing synthetic AIS with real AIS later

Nothing in `processing.py`, `scoring.py`, or `ranking.py` imports from
`synthetic_ais.py`. To use real data:

1. Export/convert the real AIS feed into a CSV with exactly the columns
   in "AIS schema" above (write a small one-off adapter script if the
   real source uses different column names/units — e.g. NOAA's
   `BaseDateTime`/`LAT`/`LON`/`SOG`/`COG` — that's the only place format
   differences should be handled).
2. Point `main.py` at it: `python -m module5_ais.main --ais-csv path/to/real_ais.csv --generate-synthetic=false` (i.e. just omit `--generate-synthetic` and make sure the path exists).
3. Nothing else changes. The filtering, scoring, and ranking logic has
   no idea whether the data is real or synthetic.

## Limitations

- Trajectory scoring is a transparent heuristic, not a physics-based
  maneuvering/drift model — it will be wrong for unusual vessel behaviour
  it wasn't designed to capture (e.g. sharp evasive turns).
- Isolation Forest anomaly detection runs on a very small sample (the
  candidate pool only) — treat its output as experimental, not validated.
- Real AIS coverage for Indian waters is not currently available through
  any open/public source at the time of writing; the demo pipeline is
  validated against synthetic data designed to mimic a plausible scenario.
- The `origin_zone.type == "circle"` assumption will need extending if
  Module 4 starts producing polygon-shaped origin zones instead.

## Possible future improvements

- Speed-profile matching in `trajectory_score` (e.g. detecting slowdowns
  consistent with a discharge event).
- Fit the Isolation Forest on a large background AIS sample instead of
  just the candidate pool.
- Support polygon `origin_zone` shapes from Module 4.
- MovingPandas-based stop/loiter detection if richer AIS history becomes
  available.
